# Audit e-commerce FAMMA MENNOU — 18 août 2026

Deuxième passage. Le premier (`audit-famma.html`, 14 août) portait sur un site
dont la boutique était encore fermée. Quatre jours de travail plus tard, la
boutique est ouverte, le design system est posé, la carte produit et l'écran de
confirmation sont livrés. Ce rapport reprend tout à zéro : test réel du parcours
sur le site en marche, puis lecture du back et du front.

---

## 1. Périmètre et méthode

**Site testé** : `http://localhost:8080` — pile Docker en marche (`famma_wp`,
`famma_db`, `famma_wpcli`, `famma_mail`), WordPress 7.0.4, WooCommerce 11.0.1,
thème Kadence 1.5.2 + enfant `famma-child`, plugin `famma-core` 0.2.0.

**Ce qui a été exécuté**

| Vérification | Outil | Résultat |
|---|---|---|
| Parcours accueil → boutique → fiche → panier → checkout | navigateur, 375 px puis 1280 px | fait |
| Version arabe `/ar/` | navigateur + HTML brut | fait |
| Erreurs console / requêtes réseau | navigateur | 0 erreur JS ; 1 POST avorté (voir B1) |
| `php -l` sur 19 fichiers PHP du projet | PHP 8.3.33 dans le conteneur | **0 erreur** |
| `phpcs` ruleset WordPress | phpcs via conteneur | **19 erreurs** (voir Y1) |
| `debug.log` avec `WP_DEBUG=1` + `WP_DEBUG_LOG=true` | conteneur | **fichier absent → 0 warning/notice/deprecated** |
| État réel des données (produits, avis, commandes, options) | WP-CLI + SQL | fait |
| Graphe de code | `graphify . --update --code-only` — 455 nœuds, 611 arêtes | rafraîchi avant lecture |

**Ce qui n'a pas été exécuté, et pourquoi**

- **Aucune commande n'a été passée.** Le §12 interdit les fausses commandes en
  base ; poser une commande de test est donc une décision qui vous appartient.
  C'est aussi le trou le plus grave de l'état actuel — voir **B5**.
- **Aucun rendu pixel.** Le volet navigateur n'était pas affiché, donc pas de
  capture d'écran. La vérification visuelle s'est faite sur le DOM, le CSS et les
  requêtes réseau, pas sur l'image.
- **Aucune ligne de code écrite** ce passage : la règle 1 (Context7 avant tout
  code touchant une bibliothèque externe) ne s'est pas appliquée. Un seul point
  de ce rapport demande une confirmation documentaire, il est signalé (D6).

## 2. Verdict

**Le code est bon. Les données et la configuration ne le sont pas.**

C'est l'inverse de ce qu'on voit d'habitude, et c'est une bonne nouvelle : le
socle technique — machine à états COD, sécurité des entrées, HPOS, RTL par
propriétés logiques — est d'un niveau que peu de boutiques tunisiennes
atteignent. `php -l` est propre, aucun warning PHP n'est produit avec le mode
debug actif, et la séquence nonce → capacité → assainissement → échappement est
réellement appliquée, pas récitée.

Ce qui bloque n'est pas de l'ingénierie, c'est de l'hygiène :

1. un **actif publicitaire Meta de production est branché sur le site de
   développement**, token compris, stocké dans la base et non dans `.env` ;
2. ce même plugin **déclenche `Purchase` au checkout**, ce qui contredit la règle
   non négociable « payé seulement à la livraison » et fait apprendre les
   campagnes sur des commandes non encaissées ;
3. des **produits, un avis et un visuel de test sont en ligne**, et alimentent
   une bande « Ils nous font confiance 5,0/5 » ainsi qu'un `aggregateRating`
   envoyé à Google ;
4. l'**accueil se contredit** — quatre produits, puis « le catalogue n'est pas
   encore ouvert » ;
5. le **parcours COD n'a jamais tourné** : zéro commande en base.

**Prêt pour la mise en ligne : non.** Compter 1 à 2 jours sur les cinq bloquants,
puis un test de commande de bout en bout. Les majeurs (M1–M8) valent une
semaine ; aucun ne demande de réécriture.

## 3. Bloquants

### B1 — Un token Meta de production dort dans la base, hors `.env`

Le plugin `official-facebook-pixel` (5.2.2, **actif**) détient dans
`wp_options.facebook_fbl4b_config` :

- `fbl4b_pixel_id` = `1061419273284333`
- `fbl4b_pixel_name` = `Fammamennou.tn`
- `fbl4b_business_id` = `1339755868270781`
- `fbl4b_access_token` = jeton de 448 caractères (non reproduit ici)

et `facebook_capi_integration_status` = `1`, c'est-à-dire **l'API Conversions du
plugin est allumée**.

Trois conséquences, chacune suffisante à elle seule :

1. **Le site de dev parle à l'actif de prod.** Chaque page vue, chaque ajout au
   panier sur `localhost:8080` part vers le pixel réel « Fammamennou.tn ». Le jeu
   de données publicitaire est en train d'être pollué par des tests. La requête
   `POST /?ob=open-bridge/events` observée sur l'accueil en est la trace directe.
2. **Le secret est dans la base, pas dans `.env`.** Violation de §8/§17/§41. Toute
   sauvegarde SQL — et `backups/` existe — emporte le jeton. `.env` est bien
   ignoré par Git ; la base, non.
3. **L'architecture prévue est contournée.** `FAMMA_META_PIXEL_ID`,
   `FAMMA_META_ACCESS_TOKEN`, `FAMMA_GA4_MEASUREMENT_ID`,
   `FAMMA_TIKTOK_PIXEL_ID` sont **tous vides**. Le `Tracking`/`Capi` de
   `famma-core` est donc totalement inerte : le suivi réel est fait par un plugin
   tiers, selon ses règles, pas les vôtres.

**Correctif** — dans l'ordre : révoquer le jeton dans Meta Business (il est
compromis dès lors qu'il vit dans une base de dev), désactiver puis supprimer
`official-facebook-pixel`, remettre `META_PIXEL_ID` / `META_ACCESS_TOKEN` /
`META_TEST_EVENT_CODE` dans `.env`, `docker compose up -d` pour régénérer
`wp-config.php`. En local, `META_TEST_EVENT_CODE` doit être rempli pour que les
événements atterrissent dans « Événements de test » et non dans les données
réelles.

### B2 — Deux `Purchase` par commande, dont un qui viole la règle COD

`famma-core` n'émet `Purchase` que sur la transition vers « livré »
([famma-core.php:1242](../wp-content/plugins/famma-core/famma-core.php)),
avec un `event_id` de déduplication. C'est exactement le §2.

Le plugin Facebook officiel, lui, câble son intégration WooCommerce et déclenche
`ViewContent`, `AddToCart`, `InitiateCheckout` et **`Purchase` au moment du
checkout**. Les deux systèmes sont actifs en parallèle.

Donc, dès la première vraie commande :

- **deux `Purchase`** avec des `event_id` différents → aucune déduplication
  possible côté Meta, conversions gonflées ;
- le `Purchase` du plugin part **avant** que l'argent soit encaissé. Sur du COD
  tunisien, où le refus à la livraison se compte en dizaines de pourcents,
  l'algorithme d'enchères apprend à trouver des gens qui commandent — pas des
  gens qui paient. C'est la façon la plus rapide de brûler un budget publicitaire.

**Correctif** : un seul émetteur. Supprimer le plugin (B1) et laisser
`famma-core` seul maître du sujet. Puis traiter M3, qui est l'autre moitié du
problème.

### B3 — Produits, avis et visuel de test en ligne

En base, publiés et visibles :

| ID | Titre | Prix | Note |
|---|---|---|---|
| 149 | Produit teste 3 | 50 | — |
| 144 | Produit test 2 | 80 → 40 | 5/5 |
| 141 | Produit teste 1 | 140 → 70 | — |
| 77 | teste11 | 120 → 60 | — |

Plus l'avis `comment_ID = 98` sur le produit 144 : auteur **`famma_admin`**
(votre propre compte admin), contenu « Note teste », note 5, `verified = 0`.

Cet unique avis de test se propage partout :

- bande **« Ils nous font confiance — 5,0/5 — Basé sur 1 avis client »** sur
  l'accueil ;
- étoiles sur la carte boutique et sur la fiche produit ;
- et surtout **le JSON-LD de la fiche** contient
  `"aggregateRating":{"ratingValue":"5.00","reviewCount":1}` plus un objet
  `Review` avec un `Person` auteur. Ce balisage part vers Google.

Un avis écrit par le marchand sur son propre produit, balisé comme avis client,
c'est une violation de la politique « avis » de Google (risque d'action manuelle
sur les résultats enrichis) autant que du §58/§60.

À cela s'ajoute un visuel `istockphoto-105630618-2048x2048-1.webp` dans la
médiathèque, utilisé comme illustration produit — origine et droits à vérifier.

**Correctif** : supprimer l'avis 98, supprimer ou dépublier les quatre produits
de test, recalculer les agrégats de note, retirer le visuel iStock. Reprendre
avec les trois vrais produits, coût d'achat renseigné.

### B4 — L'accueil se contredit sur son premier écran

Le gabarit [front-page.php](../wp-content/themes/famma-child/front-page.php) rend,
dans l'ordre : héros → catégories → nouveautés → **contenu éditorial de la page
« Accueil »** → pourquoi FAMMA → avis → bande WhatsApp.

Or le premier bloc du contenu éditorial de la page 35 dit, mot pour mot :

> Les premiers produits arrivent — استنّاو الجديد
> Le catalogue n'est pas encore ouvert. Aucun produit n'est en ligne pour le
> moment — nous préférons ne rien afficher plutôt que d'afficher n'importe quoi.

Il est affiché **juste en dessous des quatre produits**. Le visiteur lit une
grille de produits, puis qu'il n'y a pas de produits.

Ce n'est pas un bug de code : les sections pilotées par la donnée s'effacent bien
toutes seules (`famma_child_home_new_products()` sort si la liste est vide, et
`famma_child_home_reviews()` sort à zéro avis). C'est le texte éditorial, écrit
quand la boutique était fermée, qui n'a pas suivi.

**Correctif** : éditer la page 35 et remplacer ce bloc par le vrai discours
d'ouverture. Tant qu'on y est : la section suivante, « Une question ? عندك سؤال؟
أحكيلنا على واتساب », contient le shortcode `[famma_whatsapp]` qui ne rend
**rien** faute de numéro (M8) — un titre qui invite au contact, au-dessus du vide.

### B5 — Le parcours COD n'a jamais été exécuté

`wp wc shop_order list` renvoie **zéro commande**. Aucun `debug.log` n'existe non
plus, ce qui confirme qu'aucun code de commande n'a jamais tourné.

N'ont donc jamais été vérifiés à l'exécution :

- la soumission du checkout et le refus d'un numéro tunisien invalide ;
- les transitions confirmée → en cours → expédiée → livrée ;
- la pose de `_famma_cod_paid` et le passage en « payé » au seul statut
  « livrée » ;
- la réservation de stock à « confirmée » et sa libération sur annulation /
  refus / retour / échec de livraison ;
- l'écran de confirmation `famma_child_cod_next_steps()`, accroché à
  `woocommerce_thankyou_cod` — inatteignable sans commande ;
- l'envoi serveur du `Purchase`.

Le §11.3 exige ce test avant de considérer la tâche terminée. La logique est
correcte à la lecture — c'est écrit et documenté avec soin — mais « correct à la
lecture » n'est pas « vérifié ».

**Ce qu'il me faut de vous** : l'autorisation de passer **une** commande de test
clairement marquée (nom « TEST — à supprimer »), de la faire transiter jusqu'à
« livrée », de relever le résultat, puis de la supprimer. Dites-moi oui et je le
fais dans la foulée.

## 4. Majeurs

### M1 — Une phrase en anglais sur le checkout

`woocommerce_checkout_privacy_policy_text` est resté à la valeur par défaut :

> Your personal data will be used to process your order, support your experience
> throughout this website, and for other purposes described in our
> `[privacy_policy]`.

Elle s'affiche telle quelle, en anglais, juste au-dessus du bouton
« Commander » — sur l'écran où le client hésite le plus. Correctif : une option à
réécrire en français, avec la version derja si vous le souhaitez.

### M2 — On fait accepter des CGV qui n'existent pas

Le checkout impose « J'ai lu et j'accepte les conditions générales * ». La page
liée (ID 43) contient :

> À compléter par le propriétaire : l'intégralité de cette page, à faire valider
> par un conseil juridique.

Le refus de générer du faux texte légal est **la bonne décision** (§60) et je ne
propose pas de la changer. Mais l'état actuel — case obligatoire pointant sur un
document vide — est pire que les deux extrêmes. Même chose pour
`/retours/`. Correctif : dépublier ces pages (et retirer l'obligation) jusqu'à ce
que le texte existe, ou obtenir le texte avant l'ouverture. C'est un arbitrage,
il vous revient.

### M3 — Aucun signal publicitaire en milieu d'entonnoir

`famma-core` n'émet qu'un seul type d'événement, `Purchase`
([famma-core.php:1454](../wp-content/plugins/famma-core/famma-core.php)). Pas de
`ViewContent`, pas de `AddToCart`, pas de `InitiateCheckout`. Côté Google, seul
`gtag('config')` est posé : GA4 reçoit `page_view` et rien d'autre — les rapports
e-commerce resteront vides.

Sur une boutique COD, c'est structurellement bloquant pour la publicité : le
`Purchase` arrive 3 à 7 jours après le clic, et seulement pour la fraction des
commandes réellement livrées. Meta n'a pas de quoi optimiser. La pratique
courante est d'optimiser sur un événement de milieu d'entonnoir
(`InitiateCheckout` ou un `AddToCart` qualifié) et de garder le `Purchase`
serveur pour mesurer la vérité économique — ce que `famma-core` fait déjà bien.

Correctif : ajouter `ViewContent` (fiche), `AddToCart` (ajout panier),
`InitiateCheckout` (checkout) côté navigateur **et** les équivalents GA4
(`view_item`, `add_to_cart`, `begin_checkout`, `purchase`), chacun conditionné à
la présence de son identifiant en `.env`, comme le reste de la classe `Tracking`.

### M4 — Le `Purchase` serveur peut être rejeté par Meta

famma-core.php:1455 :

```php
'event_time' => $order->get_date_created() ? $order->get_date_created()->getTimestamp() : time(),
```

L'horodatage envoyé est celui de la **création** de la commande. Meta refuse un
événement daté de plus de sept jours. Une livraison à J+8 — banale sur un retour
en tournée ou un client injoignable — produit un rejet silencieux : l'événement
n'existe nulle part, et rien dans les notes de commande ne dit qu'il manque une
vente.

Correctif : utiliser l'horodatage de la livraison, ou borner l'horodatage de
création à « maintenant moins six jours ».

### M5 — Un `Purchase` perdu est perdu pour de bon, et l'admin attend 8 secondes

`Capi::send_purchase()` incrémente `_famma_capi_attempts` et compare à
`MAX_ATTEMPTS = 5`. Mais la méthode n'est appelée que par l'action
`famma_capi_purchase`, elle-même déclenchée par la seule transition vers
« livré ». **Il n'existe aucune reprise** : pas de cron, pas de tâche planifiée.
Le compteur à 5 tentatives est du code mort — en pratique, une tentative unique.

Un timeout réseau au mauvais moment = vente absente de Meta, récupérable
seulement en repassant le statut à la main.

Second effet : `wp_remote_post` avec `'timeout' => 8` tourne **dans la requête
admin**. Marquer une commande « livrée » peut donc geler l'écran huit secondes.
Sur une tournée de vingt commandes, c'est presque trois minutes d'attente.

Correctif : passer l'envoi dans Action Scheduler — déjà présent
(`action_scheduler_run_queue` est planifié) et livré avec WooCommerce. Une seule
modification résout la reprise, les tentatives et la latence.

### M6 — Les statuts WooCommerce d'origine restent cliquables

Quinze statuts sont enregistrés. Aux neuf du flux COD s'ajoutent « Attente
paiement », « En attente », « En cours », « Terminée », « Remboursée »,
« Échouée », qui n'ont aucun sens ici mais restent sélectionnables dans la liste
des commandes.

Le scénario coûteux : un clic sur **« Terminée »** au lieu de **« Livrée »**.
`mark_cod_paid_on_delivery()` ne tourne pas, `_famma_cod_paid` n'est pas posé,
aucun `Purchase` ne part, et le tableau de bord — qui ne compte que `delivered` —
ignore la vente. Le chiffre d'affaires réel et le chiffre affiché divergent, sans
aucun signal.

Correctif : masquer les statuts inutilisés du sélecteur, ou traiter `completed`
comme un alias de `delivered` dans `mark_cod_paid_on_delivery()`. La première
option est plus honnête.

### M7 — Les polices de la marque ne sont pas chargées

`assets/fonts/` ne contient qu'un `README.md`. Les six `.woff2` attendus par
`famma_child_font_files()` sont absents, donc
`famma_child_fonts_available()` renvoie `false`, donc `fonts.css` n'est **jamais**
mis en file et aucun `preload` n'est émis — confirmé sur le HTML rendu : zéro
`rel="preload"`, zéro requête `fonts.css`.

Le garde-fou est excellent (pas de 404 sur un thème fraîchement cloné, repli
système déclaré dans `--famma-font`). Mais le résultat vécu est que **le site
tourne en polices système** : l'identité typographique n'existe pas encore, et le
texte arabe/derja s'affiche dans la police arabe par défaut de l'appareil du
visiteur — différente sur iOS, Android et Windows.

Correctif : déposer Poppins 400/500/600/700 et Noto Kufi Arabic 400/700 en
`.woff2` dans `assets/fonts/`. Tout le reste est déjà en place et s'allumera seul.

### M8 — WhatsApp, premier canal de conversion en Tunisie, est éteint

`FAMMA_WHATSAPP_NUMBER` est vide. Conséquences en cascade, toutes constatées :

- section « Une question ? عندك سؤال؟ » de l'accueil : titre sans bouton (B4) ;
- écran de confirmation : le bouton « Corriger ma commande » ne rend rien ;
- boutique vide : le CTA de secours de `no-products-found.php` disparaît ;
- « Pourquoi choisir FAMMA ? » : la quatrième raison (« Une équipe joignable »)
  ne s'affiche pas — c'est voulu et bien fait, mais la promesse manque ;
- bouton flottant global : absent.

Le code est correct — tout est conditionné, rien ne casse. Il manque une valeur.
C'est à vous de la fournir (`ClaudeMemo` §« ce que le propriétaire fournit »).

## 6. Mineurs et dette

- **D1 — Tailles de fichiers.** Le §6 fixe le seuil de découpe à ~200-250 lignes.
  Réalité : `famma-core.php` **1 972**, `functions.php` **764**,
  `inc/shop-widgets.php` **738**, `inc/shop.php` 590, `style.css` **923**,
  `layout.css` 807, `shop.css` 703. Le §7 demande par ailleurs de **ne pas**
  éclater le plugin sans raison. Les deux règles se contredisent : à trancher
  explicitement, puis à écrire dans `ClaudeMemo.md`. Mon avis : garder le plugin
  en un fichier tant qu'il ne dépasse pas ~2 500 lignes, mais scinder
  `shop-widgets.php` et `functions.php`, qui mélangent des responsabilités.
- **D2 — Cron orphelins.** `jetpack_clean_nonces` et `jetpack_v2_heartbeat` sont
  planifiés alors que Jetpack n'est pas installé. Résidus à purger.
- **D3 — Page fantôme.** « Refund and Returns Policy » (ID 10, brouillon,
  anglais), gabarit WooCommerce par défaut. À supprimer.
- **D4 — Chaînes arabes en dur.** `أطلب توا` (barre collante), les trois étapes de

## 7. Ce qui est solide

Le dire précisément a autant de valeur que la liste des défauts — c'est ce qu'il
ne faut pas casser en corrigeant le reste.

**Qualité PHP.** `php -l` propre sur les 19 fichiers du projet. **Aucun
`debug.log` n'a été créé** alors que `WP_DEBUG = 1` et `WP_DEBUG_LOG = true` sont
bien actifs : zéro warning, notice ou `deprecated` produit par le code du projet.
Le §11.2 est tenu.

**Sécurité.** La séquence du §4 est réellement exécutée, pas déléguée :
`save_fields()` revérifie le nonce `woocommerce_meta_nonce`, puis
`current_user_can( 'edit_product', $id )`, puis `wc_clean( wp_unslash( … ) )`
(famma-core.php:583-607). Aucun `$_POST` brut, aucune requête SQL concaténée dans
le code du projet. Côté thème, le seul `$_GET` est assaini
(`inc/shop-widgets.php:125`) et les rares `echo` non échappés ne portent que des
littéraux (`aria-pressed`, `is-current`) — j'ai vérifié chacun.

**WooCommerce fait dans les règles.** HPOS **activé**
(`woocommerce_custom_orders_table_enabled = yes`) et compatibilité déclarée par le
plugin. Tout passe par les CRUD (`wc_get_order`, `update_meta_data` + `save`),
jamais par `postmeta` en direct. Aucune modification du cœur.

**La machine à états COD est juste, et pour les bonnes raisons.** Le garde-fou
d'idempotence utilise un marqueur propre (`_famma_cod_paid`) et non `is_paid()`,
avec l'explication de pourquoi les deux autres pistes échouaient. `processing` est
**retiré** des statuts payés — c'est le détail qui sépare un vrai suivi COD d'un
tableau de bord qui ment. Le stock est réservé à « confirmée », pas plus tôt
(les fausses commandes ne bloquent pas de stock réel), et libéré sur les quatre
issues où la marchandise revient.

**Tunisie.** Les 24 gouvernorats portent les bons codes ISO 3166-2:TN
(TN-11 → TN-83), sans trou. La validation téléphone tolère `+216` et `00216`,
retire espaces, tirets et points, puis exige huit chiffres — ce qui accepte ce que
les clients tapent vraiment.

**Secrets, côté code.** Le jeton CAPI voyage dans le **corps** de la requête et
jamais dans l'URL (avec le commentaire qui explique : une URL finit dans les
journaux d'accès). Il n'est ni journalisé, ni imprimé, ni renvoyé.
`_famma_purchase_sent` n'est écrit qu'après un vrai 2xx, ce qui laisse la commande
rejouable — le problème n'est pas la conception, c'est l'absence de rejoueur (M5).
`.env` est bien ignoré par Git, et `.env.example` ne contient aucune vraie valeur.

**RTL.** Sur **4 027 lignes de CSS**, **zéro** propriété physique
(`margin-left`, `right:` …) — la seule occurrence trouvée était à l'intérieur d'un
commentaire. Tout est en propriétés logiques. Résultat : `/ar/` rend
`<html dir="rtl" lang="ar">` avec la classe `rtl` et fonctionne **sans feuille de
style dupliquée**. C'est rare et c'est bien fait.

**Cache.** Les transients de l'accueil sont purgés sur les bons hooks —
`save_post_product`, `deleted_post`, `woocommerce_new_product`,
`woocommerce_update_product`, `comment_post`, `edit_comment` — donc un produit
publié apparaît tout de suite. Le tableau de bord est mis en cache avec un
drapeau `capped` honnête quand la limite est atteinte (§10 tenu).

**Honnêteté du contenu.** Les pages légales ne sont **pas** inventées : elles
portent des placeholders explicites listant ce que le propriétaire doit fournir.
`famma_child_home_reviews()` porte en commentaire le refus assumé du
« + 2 500 clients satisfaits / 4,8 sur 5 » de la maquette. C'est exactement le
§58, appliqué. Le seul écart vient des **données**, pas du code (B3).

**Le reste.** Image OG présente et servie (200), JSON-LD `Organization` /
`WebSite` propre, un seul `<h1>` sur l'accueil (le titre Kadence est détaché, pas
masqué), 0 erreur JavaScript en console sur les quatre pages testées, checkout
vide qui redirige proprement vers le panier.
